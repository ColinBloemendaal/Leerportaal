Wired via a `View::composer('app', ...)` in `AppServiceProvider`, computed fresh per request from `TenantContext`
- [x] Bootstrap `_variables.scss` wired to CSS custom properties. New `_theme-overrides.scss`, loaded after Bootstrap, maps `--reseller-*` onto the CSS variables Bootstrap 5.3 already exposes at `:root` (`--bs-primary`, `--bs-primary-rgb` via CSS relative-color syntax, `--bs-link-color`, `--bs-font-sans-serif`, etc.) so live components re-theme per request with no rebuild. Known, documented limitation: Bootstrap's hover/active shade variants (e.g. `--bs-btn-hover-bg`) are Sass-computed at build time, not live `var()` refs, so they can't follow a runtime color change -- inherent to "no per-tenant build step" (CLAUDE.md §1), not a bug

- [x] Contrast validation — warn when a chosen color pair fails WCAG AA. Client-side, non-blocking (a warning, not a rejection, per the task's own wording): `resources/js/lib/contrast.ts` implements the WCAG relative-luminance formula directly from spec, checked against primary/secondary vs white (the pairing that actually matters here, since Bootstrap renders white text on those backgrounds by default). Verified against the two values the formula is mathematically guaranteed to produce (black/white = 21:1, identical colors = 1:1) -- no JS test runner exists in this project yet, so this was checked by hand rather than adding a whole new test framework for one utility
- [x] Logo/favicon upload with dimension + type validation, private disk. Human decision on the private-disk-vs-public-visibility tension: stored on the private `local` disk (CLAUDE.md §7) but served through a new public, unauthenticated route (`App\Http\Controllers\ResellerBrandingController`, `/branding/{reseller}/logo|favicon|login-background`) that resolves the reseller by slug and streams the file back -- so the disk itself never gets a directly guessable public URL, but the login page can still show it. Type validated by content (`image`/`mimes` rules sniff actual file signatures) rather than extension, per §7. SVG deliberately not accepted for logo/login-background -- its dimensions aren't reliably introspectable via `getimagesize()`, which would make the `dimensions` rule either flaky or a no-op. `[!]` Two feature tests (full successful-upload path, needs a real generated image) can't run on this dev machine -- the GD PHP extension isn't installed locally (confirmed: the DLL exists but is commented out in `php.ini`); added `gd` to `.github/workflows/ci.yml`'s extensions list so they run in CI, which is where they'll actually be verified. Didn't edit the machine's `php.ini` myself -- that's a system-level change outside this repo, flagging it for you instead: uncomment `extension=gd` in `C:\php85\php.ini` if you want these to run locally too
- [x] Optional custom CSS field, sanitized, with a hard character limit. New `custom_css` nullable text column on `reseller_themes`. Chose rejection over silent sanitization: `App\Rules\RejectsUnsafeMarkup` (new `App\Rules` namespace; originally named `SafeCustomCss`, renamed when the email-templates task below reused it for Markdown body validation -- the denylist isn't CSS-specific) rejects, via a `$fail` message, values containing `</style` (breakout -- the critical one), `<script`, `@import`, `expression(`, `behavior:`, `javascript:`, `vbscript:`, or `data:text/html`, rather than quietly stripping them -- silently mangling admin-submitted CSS is worse UX and less safe than a clear rejection with a reason. 10,000-character hard limit on the field itself. `ThemeCssGenerator` appends the value after the `:root` block, re-running the same denylist itself before rendering (exposed as `RejectsUnsafeMarkup::firstViolation()`, reused by both the write-side rule and this read-side check) so a row that somehow predates the rule still can't reach the page -- consistent with the generator's existing "never trust the database" stance for colors/fonts. Live preview in the theme editor injects the typed CSS into an actual `<style>` tag in the current document (not a security boundary, just a mirror of the color-field preview pattern -- the server-side rule is what actually gates what gets persisted and served to other visitors)

- [x] Implement type: `multiple_choice`. First real `QuestionType` implementation, first entry in `QuestionTypeRegistry::MAP`. `payload`: `{"options": [{"id", "text"}, ...], "correct_option_id"}`; `payloadRules()` validates structure only (min 2 options, required id/text) -- doesn't cross-check `correct_option_id` actually matches one of the options' ids, since that would need a `DataAwareRule`/closure-based rule for a schema layer with no consuming FormRequest yet, and `grade()` is already defensive about it (an unmatched id just grades incorrect, doesn't error). `grade()` treats any non-string answer (missing, wrong type, array) as incorrect rather than throwing -- an untrusted "answer" coming from a cursist's submission should never be able to crash grading. Two Vue components (`Editor`/`Player`) + `resources/js/types/questions.ts` (new file, grows one interface per type same as `blocks.ts` did, except incrementally across many commits instead of one)
- [x] Implement type: `multiple_response` (with partial credit). `payload`: `{"options", "correct_option_ids": [...]}`; `answer`: `list<string>`. Partial credit is Moodle-style: each of the N correct options is worth `points/N`; each correctly-selected option adds its share, each incorrectly-selected one subtracts it, clamped to `[0, points]` so selecting everything never scores worse than selecting nothing. Same "malformed answer -> incorrect, never throw" defensiveness as `multiple_choice`
- [x] Implement type: `true_false`. `payload`: `{"correct_answer": bool}`; `answer`: bool. Same shape and defensiveness as the previous two types, just the simplest possible payload/grading
- [x] Implement type: `open_short` (keyword/regex matching). `payload`: `{"match_mode": "exact"|"contains"|"regex", "case_sensitive": bool, "acceptable_answers": [string, ...]}` -- one list serves all three modes (literal strings for exact/contains, full regex patterns with their own delimiters for regex mode), rather than a separate field per mode. A malformed admin-authored regex is suppressed with `@preg_match` (documented as deliberate, narrow, not a stand-in for validating the pattern) rather than allowed to crash grading -- a bad pattern should never be able to take down every cursist's attempt at that question
- [x] Implement type: `essay` (manual grading + rubric). `payload`: `{"rubric": [{"criterion","points"}, ...], "min_words", "max_words"}`. First manual-grading type -- `isAutoGradable()` is `false`, and `grade()` always returns `GradeResult::pendingManualGrading()` regardless of the submitted answer's shape (even blank/malformed), since only a human can score an essay; what a grading pipeline does with an ungraded/empty submission at finalization time is the grading service's business rule, a later task, not this type's
- [x] Implement type: `matching`. `payload`: `{"pairs": [{"id", "left", "right"}, ...]}` -- one flat list, no separate cross-referenced `right_options` list; assumes `right` values are unique per question (the editor's job to enforce, not this schema-level type). `answer`: `Record<pair id, chosen right text>`. Partial credit: `points * (correct pairs / total pairs)`. Player uses a `<select>` per left prompt rather than drag & drop -- fully keyboard-accessible natively, and `matching` isn't one of the drag/hotspot types the later "keyboard + ARIA alternative" task specifically targets
- [x] Implement type: `ordering`. `payload`: `{"items": [{"id","text"}, ...]}` -- array order is the correct order. `answer`: `list<string>` of ids in submitted order. Partial credit is purely positional (`points * items in their correct index / total`), not edit-distance-based, so a single adjacent swap only costs 2 of N positions. Editor and player both use up/down move buttons rather than drag & drop -- natively keyboard-accessible, same reasoning as `matching`'s `<select>` choice
- [x] Implement type: `fill_in_blank` (cloze). `payload`: `{"template": "...{{1}}...", "blanks": [{"id","acceptable_answers","case_sensitive"}, ...]}`. How `{{id}}` markers in `template` map to `blanks[].id` and render as inline inputs is entirely the player component's job (regex-split into text/blank segments, never `v-html`) -- `grade()` only cares about the blanks list and submitted values, same partial-credit-per-item shape as `matching`/`ordering`
- [x] Implement type: `dropdown_in_text`. Same template/blanks shape as `fill_in_blank`, but each blank carries fixed `options` + a `correct_option` and grading is an exact string match rather than fuzzy/case-insensitive -- a dropdown selection has no typing variance to account for. Editor/player reuse the identical template-segment-splitting approach from `fill_in_blank`'s player, swapping the inline `<input>` for a `<select>`
- [x] Implement type: `numeric` (with tolerance). `payload`: `{"correct_answer", "tolerance"}` -- absolute `±tolerance` margin, defaulting to 0 (exact match) when omitted. Accepts a numeric string as well as an actual number for `answer`, since form inputs commonly submit numbers as strings; anything else (non-numeric string, array, null) grades incorrect rather than erroring
- [x] Implement type: `hotspot_image`. `payload`: `{"image_url", "regions": [{"id","x","y","width","height","label"}, ...], "correct_region_ids"}` -- coordinates are percentages of the image (resolution-independent), and `label` is `required` for every region specifically so the player can offer a real keyboard alternative. Same Moodle-style multi-select partial credit as `multiple_response`, kept as its own copy rather than extracted into a shared helper -- both algorithms are short enough that sharing would add more indirection than it saves. Player's actual answer-submission mechanism is a labeled `<fieldset>` of checkboxes (works with zero mouse/image interaction); the image + click overlay on top is a visual convenience for mouse/touch users, not a second, unequal path -- satisfies CLAUDE.md §5's "a type is not done without [a keyboard alternative]" for this type now, rather than deferring all keyboard/ARIA work to the later consolidated task
- [x] Implement type: `drag_drop_image`. `payload`: `{"image_url", "drop_zones": [{"id","x","y","width","height","label"}, ...], "draggable_items": [{"id","text"}, ...], "correct_placements": Record<zone id, item id>}`. Same accessibility approach as `hotspot_image`: the player's real answer mechanism is a `<select>` per labeled drop zone listing the draggable items by text (the same pattern `matching` already uses), fully keyboard-operable; the drag gesture on the image is a visual convenience layered on top, not the only path. First genuinely non-scored type -- needed a new `GradeResult::notApplicable()` (pointsAwarded null, not manual, `pointsPossible` 0.0), distinct from `pendingManualGrading()`: essay's "pending" means a human will grade it eventually, likert's "not applicable" means nothing ever will. `GradeResult::isCorrect()` generalized to return null whenever `pointsAwarded` is null (was previously gated only on `requiresManualGrading`), which covers both states correctly without adding a second flag -- existing tests for `pendingManualGrading()` still pass since its `pointsAwarded` was already null
- [x] Implement type: `file_upload`. `payload`: `{"allowed_mime_types", "max_size_bytes"}` -- describes upload constraints only; what the submitted `answer` actually references (a `Media` row, tied to an attempt) is the `quiz_attempts`/`question_answers` task's job to define, not this schema-level type.
